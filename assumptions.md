# Assumptions

- `AcceptResult` is an overlay acceptance receipt only. It should not carry live Y.Doc rewrite instructions, client remap payloads, or a replacement session section index.
- (Area C) `AbsorbResult` (from `canonical-store.ts`) is the SINGLE surviving publication-result type: a committed-canonical receipt (`commitSha`, `rewrittenDocumentPaths`, `absorbedSectionRefs`, `changedSections`). It must never grow into a live Y.Doc structural-delta contract (no Y.Doc rewrite instructions, no client/section remap, no session/DocSession mapping). The committed canonical delta reaches active live Y.Docs via the Area B/H CRDTProposalGenerator `Y.transact` canonical-to-live primitive, NOT via `AbsorbResult` and NOT via any commit-pipeline reinjection path. No resurrected `AutoCommitResult`/`PreemptiveCommitResult`; Areas I/J shape any wire DTO at their own boundary from this receipt.
- (Area C) `commit-pipeline.ts` is the single application-level proposal→canonical publication routine, renamed to `publishProposalToCanonical{,Detailed}` with `commitProposalToCanonical{,Detailed}` retained as deprecated aliases (same binding) until Areas I/J/K port callers. `commitHumanChangesToCanonical` is retired (no production callers). Manual/explicit, agent, and CRDTProposalGenerator publishes are separate callers of this one routine (spec 11) — no shared `auto-commit.ts`/session-sidecar.
- (Area C) Runtime publish-failure rollback of the transient `committing` guard state is caller-specific via `options.ownerKind` (default `"agent"`), dispatched through Area F's `rollbackCommittingProposal(id, ownerKind)`: agent→`draft`, human/DocSession→`inprogress` (spec 02 › Why `committing`). The PIPELINE owns the rollback; the CRDTProposalGenerator now passes `{ ownerKind: "docsession" }` and keeps only a defensive best-effort fallback rollback (no more double-rollback to draft-then-inprogress). Startup recovery NEVER uses this path.
- (Area C, for Area E) Re-runnable committing-recovery entrypoint: `publishCommittingProposalToCanonical(proposalId, committedMetadata?: HumanInvolvementCommittedProposalMetadata = {}, diagnostics?: string[], options?: CommitProposalToCanonicalOptions): Promise<AbsorbResult>`. It asserts `status === "committing"` (throws `InvalidProposalStateError` otherwise), publishes from `proposalContentRoot(id, "committing")` WITHOUT re-running `transitionToCommitting`, absorbs into canonical, and transitions to `committed`. Idempotency: `absorbChangedSections` uses git `--allow-empty`, so a re-run after the canonical delta already landed is a no-op-delta finalize that still yields a valid `commitSha` and advances the FSM (finalize-if-landed); a re-run before it landed simply re-absorbs (rerun-absorb). It performs NO FSM rollback on failure — recovery owns its own fail-with-report. Area E drives this entrypoint.
- Dirty-status UI should react to coarse invalidation events (`writer:dirty-state-changed`, `session:status-changed`) and then refetch authoritative state, rather than relying on per-section websocket payloads derived from live-session mappings.
- A live fragment only has a user-facing section identity when the authoritative overlay/canonical skeleton can resolve it. If a structurally dirty live fragment is ahead of that authoritative view, it is not surfaced as a named dirty section until settle assigns that authoritative identity.
- Writer-scoped dirty section attribution is captured from the server-authoritative focused heading path at the moment a fragment is marked dirty. If no focus is available, dirty persistence falls back to a doc-level placeholder instead of reconstructing section identity from fragment keys later.
- (Area A) The temporary `export { ProposalShadowContentLayer as OverlayContentLayer }` compat alias in `content-layer.ts` is RETAINED at the end of Area A because deferred-area production files still construct the session-overlay (live staging root) via `OverlayContentLayer`, which is session-overlay shadowing (NOT proposal content) owned by other areas: `crdt/ydoc-lifecycle.ts` (Area B), `storage/staged-sections-store.ts` (Area C), `storage/session-inspector.ts` (Area D/E), and the `sessionOverlay` in `storage/auto-commit.ts` (its proposal-content access was ported to `ProposalEditor`; the residual `OverlayContentLayer` is only the session staging root, deleted by Area B/C). All Area-A-owned proposal-content callers were ported off the alias. The alias removal is deferred to the area that deletes the last session-overlay consumer.
- (Area K) Bootstrap commit metadata: `bootstrap-content-seed.ts` commits the seed proposal via `commitProposalToCanonical(proposalId, {}, undefined, { commitMessageOverride: "bootstrap seed: ..." })`. The current `commitProposalToCanonical(proposalId, scores: SectionScoreSnapshot, diagnostics?, options?)` signature no longer carries any `humanInvolvement_at_commit` field, so the original open question's "soon-to-be-removed humanInvolvement shape" no longer applies. Decision: pass an EMPTY `SectionScoreSnapshot` (`{}` = zero scores, consistent with system-only seeding) and an explicit bootstrap-seed `commitMessageOverride` instead of the default `agent proposal:` message. This is the shape consistent with what `commitProposalToCanonical` currently expects and does not pre-adopt unlanded Areas C/G/Q changes.
- (Area K) Restore canonical-side deleted-section read: `restore-service.ts` continues to use `new ContentLayer(canonicalRoot)` (+ `getSectionList`) to compute deleted sections. Area A did NOT ship a standalone canonical-only reader facade (`ProposalReader` is proposal-scoped and shadows over the restored proposal content, so it cannot yield the pre-restore canonical section list). Area A's "no direct `ContentLayer`" rule was explicitly scoped to PROPOSAL-CONTENT access; canonical reads are out of that scope and several deferred-area files still read canonical via `ContentLayer`. Keeping the canonical `ContentLayer` read here is therefore Area-A-consistent. Re-home onto a canonical reader facade if/when one is introduced.
- (Area A) `ProposalEditor.writeSection` auto-create delegates verbatim to the existing engine (`ProposalShadowContentLayer.upsertSection` → `materializeAncestorHeadings`). That engine has a PRE-EXISTING limitation: a single write that introduces more than one brand-new heading segment at once (e.g. `["Getting Started","Installation","Linux"]` into a fresh document, or `["Sub","Leaf"]` where both are new) throws a skeleton-integrity error rather than materializing the whole chain — even though spec `04` "Auto-creation within ProposalEditor" says it should. Atomicity still holds (the failed write leaves no partial chain). Creating one new segment per write (incremental), or one new leaf under an existing ancestor, works. Fixing the multi-new-segment path lives in `document-skeleton.ts`/`content-layer.ts` engine code, not in the Area-A facade port, so the facade test asserts the incremental path and this limitation is recorded here rather than worked around in the facade.

## Area G decisions

- (Area G) Policy selection mechanism: a SINGLE module-level selected policy instance (`AgentWritePolicy = new HumanInvolvementCompatibilityPolicy()`) exported from `backend/src/domain/agent-write-policy.ts`. Selection is a BUILD CONSTANT, not a registry and not `AdminConfig.governance_mode`-driven hot-swap (spec/12 "Implementation Notes": "one selected Agent Write Policy", "not a hot-swap framework"). - (Area G) `ProposalTargetRef` is consumed from shared-types (Area Q already added it, aliased to `SectionTargetRef`). Area G did NOT define a competing target type.
- (Area G) The presence-based HARD BLOCK (live session / dirty files / human-proposal-lock → score 1.0 short-circuit) from the deleted `SectionGuard.evaluateBatch`/`SectionPresence` is NOT reproduced in the policy. Those concerns moved to the FSM-lock subsystem (Area F / `ProposalFsmLocks`). The human-involvement compatibility policy is now purely the recency-driven soft-block scoring plus the aggregate-impact escalation. Consequently a soft-block (per-section score ≥ threshold) carries `blockedReason: null` (no enum), because the new `HumanInvolvementBlockedReason` union only enumerates `human_proposal_lock` (FSM-owned) and `aggregate_impact`. - (Area G) Aggregate-impact escalation mapping (spec/12 open question confirmed): when every section individually passes but `computeAggregateImpact` trips, top-level `canWrite` is set false AND the single highest-scoring passing target is flipped to `canWrite: false` with `blockedReason: "aggregate_impact"` and a prose message naming the aggregate cause — preserving the old `section-guard.ts` 176-185 behaviour under the new contract rather than dropping it.
- (Area G) `buildCommittedProposalMetadata(result)` derives the per-section score snapshot (`{ globalKey -> score }`) from the policy result's targets, replacing every caller-hand-built `SectionScoreSnapshot`. Stored unchanged as `humanInvolvement_at_commit`. `transitionToCommitted` now types its third param as `HumanInvolvementCommittedProposalMetadata` (structurally identical `Record<string,number>`; coordinated additively with Area F's lock edits in the same file — no clobber).
- (Area G) Human / human-authoritative commit paths BYPASS the policy entirely (spec/12). Where a Q DTO requires a mandatory `agentWritePolicy` field on a human path (e.g. `CreateProposalResponse`, `CommitProposalAccepted`), the route passes `humanBypassPolicyResult()` (a success-phrased `canWrite:true` result with empty targets and the prose "Human writers are not governed by the agent write policy"), so humans are never shown as blocked.
- (Area G) Thin agent-commit-gate export `evaluateAgentWritePolicy(proposalId)` in `commit-pipeline.ts` delegates to `AgentWritePolicy.evaluateProposal`, giving all current callers a stable migration target. The old `evaluateProposalHumanInvolvement` + `EvaluationResult` interface are deleted.
- (Area G) Section-level read-API summary: added `AgentWritePolicy.summarizeSection(ref, commitInfoByHeading)` returning `SectionAgentWritePolicySummary`, used by `section-meta-builder.ts` and the `/heatmap` route. - (Area G) Salvage-fidelity fix: the human-involvement scoring counts ONLY HUMAN commits. The deleted `SectionRecency.getSecondsSince` gated git recency on `writerType !== "agent"`, but the surviving `getSecondsSinceLastHumanActivity` in `section-activity.ts` counts ANY commit. The policy therefore filters the per-document commit-info map to drop `writerType === "agent"` entries before scoring (`filterToHumanCommits`); without this an agent's own recent commit would block the next agent write, which is not the original behaviour. Also: a section whose heading/document cannot be resolved against canonical (e.g. a brand-new imported doc materialized only in the proposal shadow) is treated as "no recorded human activity" (score 0) rather than throwing — `safeSecondsSinceLastHumanActivity` swallows `DocumentNotFoundError`/`HeadingNotFoundError`/skeleton-integrity errors.

Heatmap/route DTO redesign and the `section-activity → section-commit-history` extraction remain Area L; Area G only did the agent-write-policy-summary + `crdt_session_active` slice needed to compile. The routes' `humanInvolvement_score` literal errors were resolved (not left for L) because Area G owns the policy-summary source and Q's new `agentWritePolicy` field is the correct replacement.

## Phase 3 MW-9

- (MW-9 root cause) The multi-new-segment auto-create failure was in `ProposalShadowContentLayer.materializeAncestorHeadings` (`backend/src/storage/content-layer.ts`), NOT in `document-skeleton.ts` and NOT in the `ProposalEditor` facade. ## Phase 3 MW-15 (live structural normalization: SPLIT + reconcile)

- (MW-15 design) The quiescence normalization now has TWO stages in `runQuiescenceCommand` (`ws/crdt-ws-coordinator.ts`). Stage 1 (unchanged, MW-2) = per-fragment HEADING-LINE canonicalization (`computeNormalizationDelta`, resolved against CANONICAL/`null`): fixes a wrong-level/duplicated heading line IN PLACE on the stable canonical fragment key. Stage 2 (NEW) = STRUCTURAL reconcile of the live fragment SET to the proposal's authoritative post-materialize layout, run once the document is quiet (`!anyStillActive`) and a current proposal exists, then a fan-out. Both stages run through the generator's `normalizeQuiescedSection` Y.transact primitive (compute-outside / apply-inside + pre-flight clock check), sequentially-awaited so each takes a fresh clock snapshot — no mutual abort.
- (MW-15 why proposal-authoritative) `materializeEdit()` routes the live edit through `ProposalEditor.writeSection`'s PARSER-DRIVEN markdown expansion, so an embedded heading typed into a fragment ALREADY becomes a real proposal section at materialize time. The structural truth (post-split) therefore lives in the proposal content tree; the live Y.Doc just hasn't been re-fragmented to match. The reconcile is "make live match `resolveLiveSectionLayout(docPath, currentProposalId)`" — the exact MW-10 re-seed shape (bulk `readAllSections` from the proposal shadow → `buildFragmentContent` per layout entry), generalized to ADD/REMOVE keys.
- (MW-15 mechanism) New structural delta `LiveStructuralReconcile {writeMap, removedKeys, addedKeys}` + `computeLiveStructuralReconcile`/`applyLiveStructuralReconcile` in `crdt/live-section-deltas.ts`. Add/update + clear happen atomically via the existing `LiveFragmentStringsStore.replaceAndClearFragmentStrings` (clears all target+removed fragments in one txn, merges populating updates in one `Y.applyUpdate`). Added a minimal removal primitive `LiveFragmentStringsStore.unregisterFragmentKey(key)` (drops the key from `orderedKeys` + writer-attribution; the Y.XmlFragment is left empty in `ydoc.share` since Y.js has no top-level-type deletion) so `getFragmentKeys()` converges to the layout. Apply clears removed fragments then unregisters their keys.
- (MW-15 GATING — the load-bearing subtlety) The structural reconcile must NOT fight the Stage-1 per-fragment canonicalizer. A wrong-level heading (e.g. `#### Overview` in a level-2 Overview) RE-KEYS the section in the proposal (`section::overview` → `section::sec_overview_…`) but does NOT change the document's section TREE (same set of heading paths). A genuine SPLIT/MERGE ADDS/REMOVES heading paths. So the reconcile gates on the heading-PATH set, computed against BOTH proposal and canonical layouts: it engages only when (a) the proposal's heading-path set differs from canonical's (split/merge), OR (b) the live set still carries a fragment key absent from BOTH the proposal layout AND canonical (a stale orphan from a prior split that a later merge dropped — the path set may already match canonical again, but the live set has not converged). When (a) tree-shape-changed, the proposal layout is fully authoritative and EVERY live key absent from it is removed (incl. a canonical key like `section::overview` that a split turned into a `--section-body--` body-holder). When only (b), the canonical-keyed survivors the per-fragment normalizer owns are PRESERVED — only the true orphans are removed. Without this gate the reconcile churned/emptied `section::overview` on a pure heading-level fix and broke the existing MW-2 wiring test.
- (MW-15 SPLIT — DONE, tested live end-to-end) An author types `## Overview\n\nbase\n\n### New Sub\n\nsub` into the Overview fragment; materialize splits it (proposal layout = BFH, `--section-body--`(Overview body-holder), `sec_new_sub_`(New Sub), Timeline); at quiescence the reconcile ADDS the body-holder + New Sub live fragments with correct bodies, REMOVES the old `section::overview`, and the survivors keep identity. - (MW-15 ORPHAN→PREDECESSOR MERGE — REMOVE mechanism done + unit-tested; end-to-end trigger SCOPED OUT with precise reason) The reconcile's REMOVE path (what a merge needs) is implemented and unit-tested directly: split, then `ProposalEditor.deleteSection(["Overview","New Sub"])` shrinks the proposal layout, then the SAME `computeLiveStructuralReconcile`/`applyLiveStructuralReconcile` pair removes the orphaned `sec_new_sub_` live fragment while preserving Timeline's identity+content and the Overview body-holder (test `live-structural-normalization.test.ts` (2)). HOWEVER the END-TO-END orphan→predecessor merge cannot be provoked through the QUIESCENCE TRIGGER, because that trigger fires through `materializeEdit()` and the materialize path CANNOT re-snapshot a post-split body-holder section: after a split the Overview body-holder is `{headingPath:["Overview"], heading:"", level:0}`, and a second `ProposalEditor.writeSection` with an empty heading on a NON-BFH heading path throws `"Illegal arguments: targeting a headed section but missing the section heading"` (`content-layer.ts validateUpsertHeadingArgument`). Fixing it is a materialize/`writeSection` body-holder contract change (it must accept re-snapshotting a body-holder via headingPath+level without a heading), out of MW-15's scope. So the merge MECHANISM ships and is tested; the merge TRIGGER is honestly deferred to that materialize fix.

## C1 decisions (reconstructed DocSession adopts the existing `inprogress` proposal)

- (C1) On DocSession reconstruction, `constructDocSession` (`backend/src/crdt/ydoc-lifecycle.ts`) ADOPTS the existing CRDT-owned `inprogress` proposal for the doc instead of orphaning it: the session reuses `existingInProgress.docSessionId` as its own `docSessionId` (falling back to `crypto.randomUUID()` only when there is no proposal to adopt), AND the proposal id is passed explicitly to the generator as `initialProposalId` (assigned to `currentProposalId` in the constructor). The explicit id is the load-bearing binding; the docSessionId reuse is the redundant belt-and-suspenders so the lazy `ensureCurrentProposal` lookup ALSO resolves to the same proposal. This fixes the fork-a-second-proposal bug where a fresh `docSessionId` made the first post-restart edit miss and create a duplicate `inprogress` proposal (violating spec-10 "one active proposal per DocSession").
- (C1 edge case a — legacy/missing docSessionId) A proposal lacking `docSessionId` is, by definition (`isCrdtOwnedProposal`), NOT CRDT-owned and is filtered OUT by `listInProgressProposalsForDoc` (the filter requires `docSessionId !== undefined`). So a "legacy inprogress proposal missing its docSessionId" is invisible to this adoption path and `existingInProgress` is null for it — there is no live code path where we adopt a proposal whose `docSessionId` is missing. The `initialProposalId` binding is nonetheless wired as the primary mechanism (rather than relying on docSessionId keying) so adoption stays correct even if the keying scheme changes; the `?? crypto.randomUUID()` docSessionId fallback only triggers in the no-proposal case.
- (C1 edge case b — duplicate proposals) `findInProgressProposalForDoc` returns only the first match. To avoid silently picking one when the one-active-proposal invariant is violated on disk, reconstruction now calls the new `listInProgressProposalsForDoc(docPath)` (plural) and, if it returns MORE THAN ONE proposal, `console.error`s the offending ids and THROWS, refusing to reconstruct the session rather than orphaning the extras. Post-C1 this state should be impossible; refusing surfaces corruption loudly instead of compounding it.
- (C1 → C4 dependency, noted not blocked) Once adoption works, a reconstructed session's first edit materializes into the adopted proposal. If C4 (touched-section-scoped materialization) is still unfixed, that first materialize re-snapshots the whole doc and the adopted proposal will (wrongly) re-lock the entire document. This is a C4 concern; C1 is correct and complete independent of it.

## C2 decisions (publish-pause deadlock fix — readiness wait off the actor lane)

- (C2 root) The deadlock was a lane-held wait: `runPublishAttempt` ran as ONE actor-lane command that `await`ed the readiness promise, while `doc_publish_ready` acks (and pause-disconnects) were relayed by ENQUEUING `markReady`/`handleSocketDisconnect` onto the SAME serial lane — so the ack could never run and the publish only resolved via the 10s timeout → aborted. Fixed by a SIMPLIFICATION, not a redesign: the wait no longer occupies the lane.
- (C2.1) `markReady` and `handleSocketDisconnect` are now called DIRECTLY (synchronously, off the lane) from the `MSG_DOC_PUBLISH_READY` handler and the socket-close handler. The spec-10 step-6 ordering proof still holds: `handleMessage` for `MSG_YJS_UPDATE` `await`s its enqueued lane command, and the per-socket message chain is FIFO, so a socket's earlier Yjs updates are fully materialized before its later `doc_publish_ready` frame is even read. The readiness WAIT must not occupy the lane precisely because a lane-held wait would STARVE those very updates (queued update command can't run → its frame's handler never resolves → the ready frame behind it is never read).
- (C2.2) `runPublishAttempt` is split into: Phase 1 (short lane command: guard + snapshot `activeEditorSocketIds` + `publishPause.start()` + fan out `doc_publish_pause_start`, then RETURN, freeing the lane); Phase 2 (await readiness OUTSIDE the lane); Phase 3 (second lane command: `finalizeAndEnd` = commit-if-ready, ALWAYS `end()` the pause + fan out `doc_publish_pause_end` in a `finally`). An EMPTY required-editor set is trivially settled, so Phase 1 finalizes INLINE (no off-lane hop) — this keeps the autonomous / last-editor fast path synchronous, which is also why the existing `live-session-wiring` autonomous-publish test (no editor sockets) still observes the publish via a single lane drain.
- (C2.2 concurrency) Concurrent publish attempts for the same doc are SERIALIZED via a module-level `publishChains` map: a new attempt waits for any prior attempt to FULLY complete (through `end()`) before its own Phase 1 runs, so two attempts never share the pause FSM concurrently. This is what makes the close-handler sequence correct (a last-editor disconnect aborts the in-flight quiescence pause, that attempt ends, THEN the chained last-editor publish starts fresh with an empty required set and commits). Phase 1 guards on `publishPause.getState() !== "idle"` (stricter than `isActive()`) so `start()` is only ever called from idle and never throws.
- (C2.3) Entry-point audit: (a) the quiescence command (`runQuiescenceCommand`, itself a lane command) now branches — empty required set → `await publishInlineOnLane(session)` (inline, no off-lane wait, safe on the lane); non-empty → `void runPublishAttempt(session)` (fire-and-forget; awaiting it inside the lane command would re-deadlock the Phase 1 enqueue behind the still-running quiescence command). (b) `requestDocSessionPublish` and `publishOnLastEditorDisconnect` call `runPublishAttempt` DIRECTLY (off-lane), never wrapped in `session.enqueue`.
- (C2.4) Typed publish outcome `PublishAttemptOutcome { outcome: "committed" | "noop" | "aborted" | "failed"; message? }` (derived from `PublishResult` + the pause result). `requestDocSessionPublish` now RETURNS it (was `void`) so restore/overwrite (C5) can branch on the pre-handoff publish result. `runPublishAttempt` never rejects.
- (C2 test seam) Added `registerFakeEditorSocketForTest(docPath, socketId)` to the coordinator (TEST-ONLY export) so the publish-pause readiness flow can be driven with a non-empty required-editor set without a live WebSocket + mode-transition handshake. The deadlock regression (`__tests__/crdt/publish-pause-deadlock.test.ts`, 4 cases) was verified to FAIL/hang when the readiness wait is moved back inside the Phase 1 lane command, and to PASS after the split. Cases: (1) lane-free-during-wait + off-lane ack commits; (2) multi-editor all-must-ack; (3) required-socket-disconnect aborts (proposal stays inprogress); (4) readiness ordering invariant — a prior update enqueued before the off-lane `markReady` is committed because Phase 3 finalize is enqueued behind it (FIFO lane order).

## C3 decisions (single server-applied-delta broadcast; no raw-bytes relay)

- (C3) `MSG_YJS_UPDATE` propagation collapsed to ONE mechanism (spec 05 §Fragment Injection / §Structural Normalization). `processArbitratedClientUpdate` captures `beforeSV = Y.encodeStateVector(ydoc)` before applying the inbound update, applies + arbitrates + reverts blocked fragments, then ALWAYS broadcasts the net applied delta to ALL sockets (sender included): `broadcastToAll(docPath, encodeUpdate(Y.encodeStateAsUpdate(ydoc, beforeSV)))`. This single delta carries the WON edits and the revert corrections; in the no-conflict case it equals the client's own update (sender re-applies idempotently). The old conditional `if (revertedAny)` FULL-state broadcast is gone.
- (C3) The raw-bytes relay `broadcastToOthers(docPath, socket, encodeUpdate(payload))` was DELETED from the `MSG_YJS_UPDATE` handler — peers now receive ONLY the single server-applied delta, fanned out from INSIDE the actor lane (so it cannot be reordered ahead of the server state it must follow). `MSG_AWARENESS`'s `broadcastToOthers` is untouched (awareness is not arbitrated Y.Doc content). The handler's now-unused `const docPath` was removed.
- (C3 test) `__tests__/crdt/single-broadcast-arbitration.test.ts` drives the REAL frame handler (`handleMessageForTest`, a new TEST-ONLY export) with a sender + a peer socket (peer's outbound frames applied to a replica Y.Doc). It asserts the peer receives EXACTLY ONE `MSG_YJS_UPDATE` frame and converges to server truth (blocked edit absent; won fragment present in the mixed case). Verified FAILING under the restored dual-broadcast code (peer received TWO frames). The single-frame count is the load-bearing distinguishing property (note: `replaceFragmentString` tombstones the blocked structs and inserts fresh ones, so a re-applied raw relay is largely idempotent content-wise — the COUNT, i.e. the existence of the forbidden second path, is what the spec forbids and what the test pins).
- (C3-perf) The pre-edit capture in `processArbitratedClientUpdate` no longer markdown-reconstructs EVERY fragment on every keystroke. It captures a single cheap binary snapshot `LiveFragmentStringsStore.captureState()` (= `Y.encodeStateAsUpdate`, O(structs), no markdown), and reconstructs pre-edit markdown for ONLY the (rare) blocked subset via `snapshotFragmentContentFromState(state, blockedKeys)` (builds one throwaway Y.Doc, reads only those keys). Correctness-neutral (the race-arbitration revert tests still pass); the common no-conflict keystroke pays zero markdown roundtrips for pre-edit capture.

## C4 decisions (per-edit materialization scoped to touched sections)

- (C4 defect #1 — over-locking, FIXED) The per-edit materialization no longer whole-doc snapshots + replaces the proposal manifest (which made a one-section live edit lock EVERY section against agents — a contention-model inversion). `materializeEdit(scope?)` / `materializeIntoProposal(proposalId, scope?)` now take an optional `MaterializeScope { touchedFragmentKeys }`. When present (per-edit path), the WRITE LOOP narrows to the touched fragments (filtered from the whole-doc snapshot by `fragmentKey`, now carried on `LiveSectionSnapshot`) and the manifest grows MONOTONICALLY via the new `unionCurrentProposalSections(id, add, remove)` (add = engine `writtenEntries` heading paths, non-sub-skeleton; remove = engine `removedEntries` heading paths; ADD wins over REMOVE so a restructured-but-surviving parent stays claimed). When absent (finalize/publish, cross-section move), behaviour is UNCHANGED: whole-doc materialize + `updateCurrentProposalSections` replace. The coordinator's `processArbitratedClientUpdate` passes `arbitration.materializeKeys` as the scope. Verified by `__tests__/crdt/per-edit-materialization-scope.test.ts` (one edit → proposal claims only that section; an agent write to an untouched section is NOT blocked by `checkProposalLocks`; the touched section IS) — confirmed FAILING when scope is neutered to whole-doc.

- (C4 task 5 — `locked_sections`) DECISION: `proposal.sections` is the SINGLE authoritative lock-claim set (the FSM lock index reads only `sections`). `locked_sections` is KEPT but always written IDENTICALLY to `sections` (in both `updateCurrentProposalSections` and `unionCurrentProposalSections`), so the two can never disagree, because `api/application/proposals.ts:220` still reads `proposal.locked_sections ?? proposal.sections`. - (C4 cross-cuts verified) `finalizeAndPublish` still whole-doc materializes (`materializeIntoProposal(id)` with no scope) so the published proposal reflects the whole live doc; `moveLiveSection` still calls `materializeEdit()` with no scope (whole-doc, correct for a structural reorder). C1 interaction: an ADOPTED reconstructed proposal's first edit now materializes TOUCHED-ONLY into the adopted proposal (no longer re-locks the whole doc) — this is exactly the C1→C4 dependency that was flagged.
- (C4 defect #2 — engine-delta-driven live reconcile / Yjs-identity transplant, DEFERRED with reason) Task C4.6 (feed the engine `fragmentKeyRemaps`/`structureChanges` into the live Y.Doc reconcile instead of `computeLiveStructuralReconcile`'s layout set-diff, TRANSPLANTING a re-keyed fragment to preserve Yjs identity) is NOT done. Reasons: (1) The headline benefit — preserving Yjs identity across a fragment-key RE-KEY — is not achievable: a live fragment key IS its top-level Y.XmlFragment name in `ydoc.share`, Yjs cannot rename a top-level type, and integrated items cannot be re-parented between top-level types, so any re-key necessarily re-mints the fragment. MW-10 already hit and ACCEPTED this exact wall ("CARET RECOVERY ... DEFERRED ... bad UX, 100% correct data"). (2) The remaining, achievable part (drive add/remove/survivor-content from the accumulated engine delta rather than the set-diff) is content-NEUTRAL — the existing set-diff `computeLiveStructuralReconcile` already produces correct content — and would require accumulating per-edit deltas across the actor lane and rewriting the delicately heading-path-gated MW-15 reconcile, i.e. real regression risk for no reachable correctness/identity gain. Decision: keep the working content-correct set-diff reconcile; revisit only if Yjs gains a fragment-rename/re-parent primitive (then the transplant becomes possible and the rewire is justified). The over-locking P0 (defect #1) is fully fixed independently of this.

## C5 decisions (forced restore/overwrite aborts on failed pre-handoff publish)
